# Workflow runtime design vs. current implementation

Compared the linked `workflow-runtime-design.md` with the implementation in `/home/pranav/cli/agav/source/workflows/`, its CLI/slash-command integrations, and the current workflow reference docs. This is a code-reading comparison; I did not run the implementation or tests in this step. The current implementation is an explicitly limited foreground JSON workflow subset, not the full runtime described in the design.

## Highest-impact gaps

1. **Most specified node types and agent composition are absent.** The design calls for `agent`, `prompt`, `tool`, `skill`, `approval`, `test`, `parallel`, `reduce`, and bounded `loop` nodes, plus native/A2A agent execution. `source/workflows/definition.ts:5-14, 22-38` accepts only `tool`, `approval`, and `job`; `runtime.ts:72-105` only dispatches those supported types. There is no agent loader/executor integration, skill activation, test assertion runner, reducer, or loop executor. This misses the design's central composition capability, not just optional polish.

2. **No parallel DAG scheduling.** The design's goals and speed strategy require independent nodes to run concurrently up to `maxConcurrency`. `source/workflows/runtime.ts:32-33, 63-80` explicitly performs sequential execution, selecting and executing one ready node per loop. There are no concurrency policies or parallel groups. Independent branches therefore do not get the promised speedup.

3. **Structured handoff/output schemas are not implemented.** The design examples use structured node outputs and references such as `${nodes.list_pending.output.envelopes}` and require `outputSchema` validation. In `source/workflows/store.ts:13`, checkpoint `output` is only a string; `runtime.ts:16-30` supports only scalar `${inputs.key}` and the exact `${nodes.ID.output}` reference, and rejects object/array values. `definition.ts` has no input declarations/defaults or output schema fields. This prevents the structured data handoff the design expects and makes many sample workflows impossible.

4. **Resume cannot detect edits to the workflow definition or invalidate changed nodes.** The design says resume skips passed nodes only when workflow/node hashes and upstream outputs still match, and that edits rerun changed nodes and downstream dependents. Current runs persist the original definition and hash (`source/workflows/runtime.ts:10-14`; `store.ts:27-34`); resume reads that checkpoint and executes its stored definition (`runtime.ts:35-36`). It does not reload a source file, compute per-node hashes, compare upstream outputs, or invalidate dependents. Editing the workflow file after a run has no effect on resume.

5. **Approval is not an interactive human gate in the described sense.** The design calls for interactive confirmation and a decision record with `decision`, `approvedAt`, `approvedBy`, and optional note; headless execution should wait. Current `runtime.ts:72` merely marks an approval node `waiting_approval`; a separate `/workflows approve|deny` command writes the node output as the string `approved`/`denied` (`source/workflows/control.ts:6-18`). There is no approval prompt callback, approver identity, timestamped decision object, or note. The prompt is only stored in the workflow definition/checkpoint. (Tool-consent prompts are separate and do not satisfy workflow approval.)

6. **Sandbox expectations for job nodes are weaker than the design's safety goal.** Job nodes start background jobs with isolation backend `none` (`source/workflows/job-node.ts`, `startOrReattachJobNode`; current reference docs also state this explicitly). A fresh job is refused when `sandboxRequired` is true, but otherwise it runs outside the OS sandbox. The design requires shell/process execution to reuse the existing sandbox and permission model. Refusing only under `sandboxRequired` is a known limitation, not equivalent to sandboxed execution. Treat job commands as unsandboxed and review this safety tradeoff before considering the design's sandbox acceptance criterion met.

## Other missing design requirements

7. **Workflow definition format/discovery is narrower than specified.** The design calls for YAML files under project/user workflow directories, normalized internally to JSON, with required `version`, `name`, `description`, optional typed `inputs`, `policies`, and `evals`. Current `loadDefinition` only reads a JSON file path (`source/workflows/definition.ts:84-86`); `description` is optional and no inputs/policies/evals are modeled (`definition.ts:16-20`). There is no workflow-name discovery/loader.

8. **Runtime limits and policies are largely absent.** There is no workflow `maxRuntimeSeconds`, `maxNodeRuntimeSeconds`, `maxIterations`, `maxConcurrency`, `stopOnFailure` policy configuration, token/cost budget, or policy resolution. Tool nodes can use `timeoutSeconds` (`definition.ts:14, 34`; `runtime.ts:87-105`), but job nodes explicitly reject it (`definition.ts:53-57`). This means the design's whole-run deadline and job-node timeout requirements are not met.

9. **Per-node runtime configuration is not preserved.** Design fields include `model`, `provider`, `effort`, `maxTokens`, `timeoutSeconds`, `allowedTools`, and `sandbox`. The current node schema only has the small tool/approval/job field set (`definition.ts:5-14, 28-35`), so it neither parses nor persists these requested static settings.

10. **Traceability/artifacts/usage are minimal.** The design asks for per-node logs, summaries, usage, artifacts, trace events, and operational log access. Current `WorkflowRun`/`NodeCheckpoint` only persist the run snapshot and basic node status/output/error/timestamps plus job metadata (`source/workflows/store.ts:10-29`). There are no separate node checkpoint files, workflow trace events, artifacts, token usage, short summaries, or workflow `logs` command. Atomic JSON writes are implemented, but that is only part of the persistence/trace design.

11. **Testing, dry-run, and eval harnesses are missing.** The design specifies validation/runtime/resume/approval/tool/test/agent/loop tests, dry-run, mocks, assertions, and fixture-based evals. No workflow-specific test file was present under `source/__tests__/` during inspection. The CLI supports validate/run/status/approve/deny/resume/cancel only (`source/cli/workflows-cli.ts:11-21, 35`); there is no `test`, `dry-run`, mock, or eval support.

12. **CLI and slash-command operations are incomplete.** The design lists workflows list, logs, stop, test, dry-run, and broader run controls. Current CLI and slash command expose validate/run/status/approve/deny/resume/cancel, with no list/logs/test/dry-run/stop command (`source/cli/workflows-cli.ts:11-21, 35`; `source/commands/workflows.ts:8-18, 24-29`).

13. **Workflow-level timeouts and cancellation outcome reporting do not match the full status model.** Run statuses are represented by the same `NodeStatus` union (`source/workflows/store.ts:10, 27-29`); there is no run-level `timed_out` trigger/deadline, and no `skipped` status or current/completed/failed/waiting-approval node ID collections from the design's sample run record. Cancellation is implemented for foreground runs and job stop settlement, but not as part of a complete run-control/status model.

14. **Some declared design statuses and checkpoint fields are missing.** There is no node `skipped` or `pending` logging/artifact/status summary behavior beyond basic pending state; `WorkflowRun` lacks `workflowVersion` separate from schema version, `currentNodeIds`, `completedNodeIds`, `failedNodeIds`, and `waitingApprovalNodeIds`. This weakens the specified status/operations surface.

15. **Tool/test path coverage is incomplete relative to design.** Current `tool` nodes use a dedicated allowlist and permission gate (`source/workflows/gated-tools.ts`), which is a useful and safer implementation of the intended reuse principle. But the design also calls for MCP-registered tools through the normal tool registry, skill/agent/test execution, and command assertions through the sandboxed command path. The workflow host currently constructs a restricted built-in registry (`source/cli/workflows-cli.ts:40-42`), so MCP tools and extensions are excluded; there is no test node to run assertions. The implementation does use `ToolRegistry.execute()` for its supported tool nodes (`source/workflows/gated-tools.ts`), so the gap is supported tool coverage, not absence of the registry execution path.

## Important differences that appear deliberate, not necessarily bugs

- The implementation has a foreground `job` node not specified in the linked design's node-type list. It executes a shell command through the background-jobs coordinator, persists a deterministic request ID, reattaches after interruption, and fails closed for uncertain job states. This is an extension, but its literal-only command, one fixed attempt (`jobRequestId` ends in `-1`, `source/workflows/store.ts:14`), and missing timeout/retry support should not be mistaken for the design's general workflow runtime.
- Tool nodes have a separate permission gate and interactive single-invocation confirmation (`source/workflows/gated-tools.ts`), and workflow approvals do not grant tool permissions. This aligns with the design's safety intent and avoids the permission bypass identified in the earlier workflow proposal.
- Checkpoints use atomic writes, a run lock, cancellation markers, and resume skips passed nodes. Running tool nodes are refused as uncertain rather than replayed; this is more conservative than the linked design's generic “re-run running nodes” rule, and avoids silently duplicating side effects. It is a documented behavioral divergence that should be reconciled explicitly rather than treated as a simple defect.
- Headless job start/stop is denied without an applicable background-job grant; `--auto-accept` does not override the headless job gate. This is consistent with fail-closed authorization, but means job nodes are not generally usable in headless CLI workflows today.

## Bottom line

The implementation appears to be an intentionally safety-focused first slice: JSON definitions, sequential foreground tool/approval/job execution, atomic run checkpoints, basic resume, gated tool calls, and background-job reattachment. It should not be assessed as satisfying the linked design's acceptance criteria as a whole. The biggest omissions are agent/tool/skill/test composition, structured outputs and schemas, workflow-change invalidation, parallel execution, policies/timeouts, approval UX/records, full trace/eval/CLI operations, and sandboxing of job-node commands. The current reference documentation largely acknowledges this subset; the mismatch is principally between the implementation's deliberately reduced scope and the broader linked design, with the unsandboxed job execution and resume-invalidation behavior deserving explicit design decisions.
